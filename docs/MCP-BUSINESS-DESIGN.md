# 110lab 五个应用的 MCP 设计

日期：2026-10-05。状态：设计已实现为 0.14.0 发布候选，配置与验证见 [实现说明](MCP-BUSINESS.md)。

本稿以本地候选 `b1b2197` 的业务代码为依据，不代表线上已经具备下述 MCP 能力。设计范围是项目立项、奖项荣誉、招新管理、公共邮箱、动态管理；需求平台现有 MCP 保留，考核和批改不扩展。

## 1. 产品方向

提供一套实验室业务 MCP，按五个应用组织工具。用户在对话中完成查询、整理、填表、准备通知和审核操作；网页继续承担复杂编辑、文件选择、逐人预览、确认及权限配置。

推荐的使用体验：

| 应用 | 用户可以直接说 | 结果 |
|---|---|---|
| 项目立项 | 把我提供的项目资料整理成自由探索项目，加入这两位成员 | 解析实际成员身份，保存项目；是否申请共同项目单独决定 |
| 奖项荣誉 | 根据这份证书填写获奖记录，关联已有项目 | 保存带证书的荣誉草稿，指出缺失字段；按指令提交审核 |
| 招新管理 | 给待面试的这三个人准备通知，面试官是张老师 | 生成三份独立邮件预览；管理员逐人检查确认后才发送 |
| 公共邮箱 | 查一下招新相关来信，帮我拟一封回复 | 展示有权读取的邮件，准备回复草稿；确认具体邮件后发送 |
| 动态管理 | 把刚审核通过的奖项整理成官网动态 | 创建可编辑草稿，展示公开发布预览；不因荣誉通过审核就自动发布 |

不新增 AI 自动评分、自动录取、后台群发、自动发布或接管外部存量招新流程。

## 2. 身份、授权和当前基础

### 一个人的身份，按应用授予能力

- 复用实验室飞书身份；服务器由令牌确定用户，参数不接受 `actor`、`role` 或代操作用户。内部稳定身份由已验证的租户与用户标识确定，姓名只用于展示。
- 登录、允许 AI 使用业务数据、允许一次发信是不同层次。现有 `mail:session` 只负责连接身份，不自动增加读简历、读信、审核和发信权限。
- HTTP 业务 MCP 使用限定资源受众的授权令牌，按用途申请 scope；不向模型返回飞书令牌、SMTP 密码或管理员共享凭据。本机 stdio 桥接负责保管其远端连接凭据。
- 实际权限为「业务授权范围 ∩ 实时实验室角色 ∩ 对象权限 ∩ 状态允许的操作」。每次调用校验；异步任务在外发前再校验，管理员被撤权后不能靠旧任务继续操作。
- 第一版的超级管理员转让、管理员增删、邮箱白名单、SMTP/IMAP 配置仍在管理页面操作；MCP 可以报告当前可用能力及缺失配置。
- 需求平台个人 MCP Key 暂不改动，不因工作台切换账号而冒用此前账号的待办或权限。

建议 scope：

| 业务 | 按需授权范围 |
|---|---|
| 基础 | `lab:identity`、`lab:directory:read` |
| 立项 | `projects:read`、`projects:write`、`projects:review` |
| 荣誉 | `honors:read`、`honors:write`、`honors:review` |
| 招新 | `recruitment:read`、`recruitment:write`、`recruitment:decide`、`recruitment:send`、`recruitment:sync` |
| 邮箱 | `mail:read`、`mail:draft`、`mail:send`，同时限制可操作邮箱 |
| 动态 | `updates:read`、`updates:write`、`updates:publish` |

0.14.0 已支持这些 scope，旧登录授权保持原范围。授权时用中文说明数据用途，普通成员不请求管理员能力。文件权限继承所属业务与对象，不创建无限制的全站文件读取 scope。

### 已有代码可以复用什么

| 应用 | 可复用 | 接 MCP 前必须补齐 |
|---|---|---|
| 立项 | 项目、成员目录、申请/审核、里程碑、版本检查和审计 | 写入幂等、分页、供 HTTP 与 MCP 共用的权限入口 |
| 荣誉 | 草稿/提交/审核、私有证书、版本检查、幂等和历史 | 文件传输与模型读取边界、结构化筛选 |
| 招新 | 官网入库、模板变量、预览摘要、异步投递、失败/不确定结果记录 | MCP 授权、可信的逐人确认记录、分页及统一操作查询 |
| 邮箱 | 身份、管理员及公共邮箱成员同步、飞书邮箱入口 | 实际收件查询、读信、草稿、回复和通用发信能力；不能只包装跳转按钮 |
| 动态 | 草稿/公开快照分离、发布/撤回、版本检查 | 业务服务层鉴权、操作人审计、写入幂等、发布确认记录 |

MCP 与网页调用同一业务服务，避免复制一套权限和状态机。不能通过伪造网页 Cookie、Origin 或 CSRF 来复用接口，也不能绕过 HTTP 层后直接裸调用存储层。

## 3. 工具设计

以下为候选工具名。所有工具提供严格的输入/输出 schema、中文描述及只读/写入标记；不是一个接受任意动作、SQL、URL 或代码的万能工具。

### 3.1 公共基础

| 工具 | 输入重点 | 返回/用途 |
|---|---|---|
| `lab_whoami` | 无 | 当前本人、实验室角色、授权范围、各业务可用性；不返回令牌 |
| `lab_members_search` | 姓名或邮箱、分页 | 通讯录中的真实成员 ID 和消歧信息；不导出完整通讯录 |
| `lab_operation_get` | 操作 ID | 当前状态、实际副作用、失败原因和可执行下一步；仍校验对应业务权限 |
| `lab_file_upload` | 用户指定的本地文件、用途、所属对象 | 本机桥接上传，返回私有 `artifactId`；远端不接受任意本地路径或 URL 抓取 |

文件上传仅限用户明确指定的附件，不扫描其他目录。第一版用于证书及邮箱附件，大小和类型按用途校验；证书沿用 PDF/PNG/JPEG、5MB 上限。已有招新简历继续走官网 PDF/DOCX、10MB 的入口，不通过 MCP 另建重复投递。

简历、证书和邮件附件采用鉴权资源读取；不返回永久公开下载地址。资源读取与工具读取执行相同权限检查。宿主不支持资源读取时提供等效的、按附件 ID 鉴权的读取适配，不能退化为公开文件 URL。模型按需读取提取文本并保留来源位置；无法解析时明确返回原因，不编造内容。解析设置资源限额，不执行附件中的宏或脚本。上传暂存建议 24 小时内清理，已关联的业务文件按既定保留策略处理；招新资料永久保留。

### 3.2 项目立项

| 工具 | 输入重点 | 权限/行为 |
|---|---|---|
| `lab_projects_list` | 关键词、阶段、本人参与、归档状态、分页 | 登录成员按现有权限查项目摘要 |
| `lab_project_get` | 项目 ID | 返回详情、成员、里程碑、近期历史及 `allowedActions` |
| `lab_project_save` | 新建/现有 ID、名称、简介、成员 ID、链接、版本 | 新建者自动成为负责人；编辑仅负责人或管理员 |
| `lab_project_apply` | 项目 ID、版本 | 负责人或管理员提交共同项目申请 |
| `lab_project_review` | 项目 ID、通过/退回、意见、版本 | 管理员处理待审项目；退回须有原因 |
| `lab_project_milestone_save` | 项目 ID；新建时标题/受派人/截止时间，或现有里程碑状态、版本 | 创建仅负责人/管理员；现有里程碑完成/重开保留受派成员权限，不扩展为任意字段编辑 |

保留现有流程：自由探索 → 待审核 → 实验室共同项目；退回修改后可以重新申请。待审项目不能边审核边改资料；所有成员仍可查看现有范围内的项目，不擅自改成仅本人可见。

模型可以拟写简介和拆解里程碑，但不能编造成员、进度或完成证据。`search_110lab_projects` 继续只查询官网展示项目；新的内部项目查询使用上述独立名称。归档/恢复可后续补充，第一版保留网页入口。

### 3.3 奖项荣誉

| 工具 | 输入重点 | 权限/行为 |
|---|---|---|
| `lab_honors_list` | 成员、项目、级别、日期、审核状态、分页 | 本人的记录、已批准的内部记录；管理员可查全部 |
| `lab_honor_get` | 荣誉 ID | 返回详情、证书引用、历史、可执行操作 |
| `lab_honor_save` | 名称、主办方、级别、奖项、日期、成员、项目、说明、版本 | 本人或管理员维护；待审/归档不可直接编辑 |
| `lab_honor_certificate_attach` | 荣誉 ID、已上传 artifactId、版本 | 验证文件内容、所属业务、上传者和记录权限，再绑定证书 |
| `lab_honor_submit` | 荣誉 ID、版本 | 草稿或退回记录提交审核 |
| `lab_honor_withdraw` | 荣誉 ID、版本 | 提交者或管理员撤回待审记录 |
| `lab_honor_review` | 荣誉 ID、通过/退回、意见、版本 | 管理员审核；退回须有原因 |

沿用国际级、国家级、省级、市级、校级、院级、实验室级、其他。无法从证书确认级别时必须说明缺失，不能根据赛事名字推定。提交者保留在获奖成员中，项目及成员来自真实记录。

已批准记录修改内容或证书后，沿用当前代码退回草稿、重新审核的规则。荣誉批准只代表内部展示；生成官网动态是独立的草稿操作，发布须另行确认。

### 3.4 招新管理

| 工具 | 输入重点 | 权限/行为 |
|---|---|---|
| `lab_candidates_list` | 组别、阶段、接收时间、通知状态、分页 | 管理员查询摘要，不默认读取全部简历和联系方式 |
| `lab_candidate_get` | 候选人 ID、所需详情范围 | 管理员查看资料、私有简历引用、流程记录和投递状态 |
| `lab_recruitment_options` | 可选模板 ID | 返回模板及变量定义、已启用邮箱、联动就绪情况和服务端发送模式 |
| `lab_recruitment_template_save` | 模板及变量定义、版本 | 管理员维护；不改变邮箱配置 |
| `lab_candidate_record` | 初筛/考核记录/面试安排/面试记录的严格类型参数 | 复用当前状态机，记录管理员提供的判断与事实；不会发送邮件 |
| `lab_candidate_decide` | 候选人 ID、录取/未通过、理由、版本 | 只执行管理员明确指定的决定；不会附带发送结果通知 |
| `lab_recruitment_notice_preview` | 候选人 ID、模板和版本、变量、可用发信邮箱 | 保存通知草稿，生成不可变预览和确认入口；没有外发 |
| `lab_recruitment_notice_send` | 已确认预览 ID、幂等键 | 逐人确认后进入投递队列，返回操作 ID |

本组仅管理员和超级管理员可用，不向普通成员开放候选人资料。处理官网接入的新流程，不导入、接管或重复触发现有外部存量流程。

通知使用的内置变量：姓名、应聘组别、面试时间、面试官姓名、面试官邮箱、面试官联系方式、地点；支持已有自定义变量机制。姓名等来源于候选人记录，不能由模板参数悄悄替换。时间显示 Asia/Shanghai；缺必填变量、有效 Reply-To 或面试安排时不得发送。

默认邮箱沿用 `noreply@110-lab.cn`，可用邮箱由超级管理员配置。面试通知 Reply-To 使用面试官邮箱；电话或微信属于展示联系方式，不是合法 Reply-To。简历转送主题仍为 `[招新简历] 姓名-应聘组别`，不能与面试邀请主题混淆。

官网投递接收和原有服务端转送策略保持独立；MCP 查询不会额外转送简历。测试发送仅进入模拟任务；真实模式必须由已授权的部署配置启用，MCP 不提供切换按钮。本次未核验线上开关，不能依据代码默认 `dry-run` 断言线上状态。

飞书联动先对应现有已配置表格写入能力。写入记录不等于飞书工作流已经执行成功；下游自动化可能发送通知，实现前必须核实目标规则，在测试目标验证。不得用 MCP 输入任意应用、表格或 Webhook 绕过超级管理员配置。

### 3.5 公共邮箱

| 工具 | 输入重点 | 权限/行为 |
|---|---|---|
| `lab_mailboxes_list` | 无 | 返回本人可用邮箱、读/写/发送能力、同步及服务就绪状态 |
| `lab_mail_messages_list` | 邮箱、文件夹、关键词、日期、分页 | 只查询授权邮箱的邮件摘要 |
| `lab_mail_message_get` | 邮箱 ID、邮件 ID | 按需读正文、附件引用及会话信息；默认不标记已读 |
| `lab_mail_draft_save` | 邮箱、收件人、主题、正文、附件；可选原邮件 ID | 新建或编辑草稿；回复保留关联，默认不“回复全部”；返回完整预览 |
| `lab_mail_send` | 已确认草稿预览 ID、幂等键 | 校验实际 From、所有收件人和授权，入队后跟踪实际结果 |

邮箱业务权限独立检查。`noreply@notify.110-lab.cn` 保持仅管理员/超级管理员可用；`noreply@110-lab.cn` 按超级管理员设置和实际邮箱成员权限决定，不自动向全员开放。邮箱密码不因可发信而向用户或模型暴露。

这是五组里依赖最多的一组。目前代码的公共邮箱成员 API 不能证明已经能读取邮件或用指定公共地址发信。实施前核实飞书对这两个邮箱的实际读/写能力、发信身份与授权方式；可用时接官方能力，否则评估服务器上已获授权的 IMAP/SMTP 配置。不自行新增付费服务、创建密钥或打开协议权限。

收发适配未完成前，状态应为 `provider_not_ready`，不注册声称可用的收发写入能力。不能通过打开飞书邮箱网页冒充 MCP 收发完成。

招新模板邮件只走招新工具，保留逐人预览、候选人记录和审计；公共邮箱工具用于普通邮件和回复，不提供绕开招新确认的批量通知捷径。同一个用户可同时拥有这两组能力，但模型使用说明必须明确分工。

### 3.6 动态管理

| 工具 | 输入重点 | 权限/行为 |
|---|---|---|
| `lab_updates_list` | 草稿/已发布、关键词、分页 | 管理员查询；不把草稿混入公开官网接口 |
| `lab_update_get` | 动态 ID | 返回当前草稿、公开版本及二者差异 |
| `lab_update_draft_save` | 标题、摘要、受限富文本块、链接、版本 | 保存草稿，不改变公众当前看到的内容 |
| `lab_update_publication_preview` | 动态 ID、发布/撤回、版本 | 展示目标官网、实际公开内容或撤回影响，生成确认入口 |
| `lab_update_publish` | 已确认的发布预览 ID、幂等键 | 将指定版本发布到官网 |
| `lab_update_withdraw` | 已确认的撤回预览 ID、幂等键 | 撤下公开快照、保留草稿及操作历史 |

第一版只管理现有动态，不恢复首页模块 CMS，也不接受任意脚本或 HTML。按当前字段限制使用标题、摘要、段落、标题块、列表、加粗和安全链接。

从项目/荣誉整理动态时保留来源 ID，正文由管理员审阅。简历、内部邮件、联系方式或其他内部资料不会因为模型建议而自动公开。

## 4. 通用交互和接口约定

### 普通操作与需确认操作

1. 查询、按明确指令保存内部资料和草稿，不额外反复弹窗。涉及同名人员、具体时间或必填信息缺失时再问。
2. 项目/荣誉审核、候选人录取等决定需要管理员明确指令，展示对象、决定和理由；模型不能根据自己的总结自动提交决定。多对象操作列出每项，逐项执行并分别报告结果。
3. 外发邮件、飞书写入、官网发布/撤回先生成精确预览。在已登录的工作台确认页面记录人的确认，然后执行；邮件保留逐人检查，不能用模型传入 `confirmed: true` 代替。
4. 确认绑定当前人、调用客户端、操作种类、对象、内容摘要、相关版本、附件摘要和发送模式；建议 10 分钟有效，只消费一次。接收人、正文、模板、角色、配置或附件改变需重新检查/确认。
5. 插件内显示同一确认页面；宿主不能显示时提供精确的已认证页面入口，完成后查确认状态。不存在可信确认渠道时返回待确认，不退化成自动执行。

### 输入、输出与失败处理

- 写操作携带 `requestId`；更新携带 `expectedRevision`。存储层字段名称可由适配层转换。同一请求 ID、同一内容返回原结果；同一 ID 换内容返回冲突。身份和权限检查先于幂等结果回放。
- 幂等提交与业务变更/任务入队原子完成；确认消费与入队也原子完成，避免确认已消耗但没建任务。跨应用不承诺整体事务，每步有独立收据。
- 列表默认 20 条、最多 100 条，稳定游标分页；不把所有邮件、简历或证书塞入一次回复。
- 详情返回 `revision`、服务器时间、`allowedActions` 和稳定的 `webUrl`；列表先返回最小摘要。`allowedActions` 只是方便客户端，执行时重新校验。
- 文件上传、通知预览、草稿保存虽没有外发，仍可能写入临时文件或业务数据，不能错误标记为只读工具。
- 通用错误码建议：`AUTH_REQUIRED`、`SCOPE_REQUIRED`、`FORBIDDEN`、`NOT_FOUND`、`REVISION_CONFLICT`、`VALIDATION_ERROR`、`CONFIRMATION_REQUIRED`、`PREVIEW_STALE`、`RATE_LIMITED`、`PROVIDER_NOT_READY`、`RESULT_UNKNOWN`。对无权访问的对象避免泄露其是否存在。
- 可重试失败与结果未知分开。未知结果先查供应商/队列或交由管理员核实，不自动重发。继续沿用招新中明确失败才允许重试的约束；第一版重试/人工核实可保留在网页。
- 入队成功只说明任务已接收；SMTP 接受只说明发信服务器已接收，不证明收件人收到或阅读。业务现有 `SENT` 映射到 MCP 时标注这一含义。
- 模拟结果明确为 `SIMULATED`，不显示“邮件已发送”。状态记录保留候选人资料接收、通知草稿、入队、模拟、供应商接受、失败、不确定等不同事实。
- 所有写入记录真实操作人、客户端、对象、动作、版本及摘要；邮件日志保存必要追踪信息，避免把完整正文、简历或凭据写入通用运行日志。
- 邮件、简历、证书、项目文案均视为待处理内容，不是允许修改权限、发信或发布的指令。读取远端图片/链接不能自动触发追踪或任意内网请求。

## 5. 实现顺序与验收

1. **公共基础 + 立项/荣誉/动态**：抽共用鉴权服务，完善幂等和审计，接入查询、草稿、提交、审核及发布确认。保留现有插件工具和资源 URI，不改用户的登录存储分区。
2. **招新**：接入查询、模板、变量预览、逐人确认、操作查询。使用虚构候选人、模拟邮件和隔离的飞书目标验证，不碰现有真实招新流程。
3. **公共邮箱**：先完成供应商读/写能力核实，再交付从查询到草稿、确认、发信与结果查询的闭环。缺能力时明确不可用，不先上空壳工具。

核心验收场景：

- 普通成员不能读取他人未公开荣誉、招新资料或未授权邮箱；不能审核立项/荣誉；管理员撤权后立即失去能力。
- 同名成员必须消歧，成员身份来自目录；没有权限或资源失效时不使用超级管理员身份兜底。
- 并发网页/MCP 修改产生版本冲突，不覆盖新内容；重复调用不新增第二条记录或第二封邮件。
- 预览后改收件人、模板、面试时间、附件、公开正文或配置，旧确认失效；已消费确认不能再次创建任务。
- 发送超时返回结果待核实；模拟任务不会在切到真实模式后自动变成真实发送。
- 已批准荣誉修改后重审；官网动态改草稿不改公开版；招新查询不触发邮件或飞书同步。
- 附件只能按授权对象读取；无公开永久地址，无通过任意 URL 获取内网文件的能力。
- 验收分别记录本地协议测试、隔离环境流程测试、插件内身份与确认流程、真实外发验证；未做的项目明确列出，不把 API 单测等同于上线可用。

本轮仅新增本设计文件，不改接口、插件配置、身份权限或生产数据，不发送邮件，不执行发布。


招新改为工作台持久化后，`lab_recruitment_feishu_preview` 与 `lab_recruitment_feishu_sync` 已撤下，旧表格配置及授权不会触发写入。面试官通知和回填由招新工作台处理；飞书应用仅发送面试安排入口，不修改其已有事件订阅。
